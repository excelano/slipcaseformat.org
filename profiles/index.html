Profiles

How containers are used for a purpose.

What a profile is

Slipcase binds a file to a flyleaf describing it and gives meaning to two keys of that flyleaf, slipcase_version and content.file. Everything else in it is left to whoever writes the container. A profile is a specification that gives the rest meaning for one purpose: which keys a records-management tool reads and acts on, what a container is when a set of documents is handed from a contractor to an owner, which additional members belong to whom.

A profile owns one top-level table of the flyleaf, named for its purpose, and one directory of members with the same name. The table names the profile by a URI, so a program never has to guess whose keys it is reading. A flyleaf can carry several profiles at once, and a tool that understands one of them preserves the others, as Slipcase already requires of every key it does not recognize.

What every profile has in common is stated once, in the framework. How every profile writes an identifier, a person, a hash, a date, and a log that shows when it has been edited is stated once, in the shared conventions, so that two profiles do not each invent a slightly different form of the same thing. The design document says why each of their rules is drawn where it is.

Slipcase Records Profile
design document		 [records] 1.0, final Slipcase Fileroom; fileroom (MIT library and command-line tool)

The Slipcase Records Profile makes a container a managed record: an identity that survives copying, a custodian, the retention series that decide how long it is kept, holds that stop its destruction, a history that cannot be edited without the edit showing, and a register that records its destruction in a hash chain anyone can verify. Each version has a page of its own that does not change, so a record can always be read against the version it declares.

Adding a profile

Anyone can write a profile, under any URI, and the framework governs it as it governs the profiles listed here. Nothing on this page makes a profile valid or invalid; writing a profile walks through what the framework asks of one.

To list a profile, open a pull request against this site's repository adding a row to the table above. What is wanted is a specification someone can read at the profile's URI, the version it has reached, and, where one exists, a program that implements it.

The table is also the record of which table names are in use. Two profiles that fix the same table name cannot be carried in one flyleaf, so listing a profile claims its table name for its URI, first come. A pull request naming a table that a listed profile already uses is refused, as is one naming a table too general to leave to a single profile. Check the table before choosing a name.

URIs under https://slipcaseformat.org/profiles/ are for official profiles, which are specified in the slipcase-profiles repository and named Slipcase Use Profile, with one word naming the purpose (FRAMEWORK §9). A profile written elsewhere takes its URI from a domain its author controls. To propose that a profile become official, open an issue on that repository.

The profiles repository at github.com/excelano/slipcase-profiles is the authority on the framework, the conventions and every official profile. This site is open to pull requests and, like every specification it carries, is dedicated to the public domain under CC0 1.0.
